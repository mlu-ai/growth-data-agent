# Governed Metric Clarification Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Return a bounded, validated metric-choice payload for ambiguous requests and route an explicit `requested_metric_name` deterministically through the governed semantic path.

**Architecture:** The local intent boundary may propose up to three metric identifiers, but the service filters and deduplicates them against the current semantic artifact and the authenticated Access Profile before exposing them. A clarification response carries safe labels generated by the service; a later explicit identifier bypasses model reinference and is checked by the same current-artifact and authorization gates as every canonical request. Trace payloads record only the clarification classification and choice count.

**Tech Stack:** Python 3.11+, Pydantic, FastAPI, LangGraph, pytest, uv.

**Spec:** GitHub Issue #96, “Return governed metric clarification choices”.

## Global Constraints

- “When a metric question is ambiguous, the governed API returns a structured clarification response containing no more than three validated metric choices.”
- “every candidate is deduplicated, validated against the current semantic artifact, and limited to governed metrics.”
- “A follow-up request using a returned `requested_metric_name` takes the normal governed route without reinference ambiguity, subject to the existing artifact and authorization checks.”
- “Responses and redacted traces distinguish an ambiguous clarification from a metric-definition gap, without logging raw question text or unapproved candidates.”
- Preserve deterministic authorization and semantic-artifact gates; do not add a UI.
